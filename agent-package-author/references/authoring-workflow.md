# Shared authoring workflow

1. Gather capability, audience, activation phrases, inputs, outputs, runtime and environment requirements, representative success and failure cases. Inventory supplied attachments, local/external files and published references before accepting requirements. Classify each as a user-authorized seed (candidate requirements), reference (facts, format authority or examples), or draft (candidate wording/implementation). Record its provenance, relevant claims and any uncertainty. The current user instruction sets task intent; applicable published format specifications govern format; attached briefs and drafts do not silently override either. For conflicting claims, compare their authority and currency, identify the concrete effect on behavior, and resolve the difference with the user when intent cannot be inferred. Record the accepted decision and an observable acceptance case before design; keep useful draft material only after checking it against the accepted contract. A brief-only request follows the same extraction and acceptance path without inventing attachments.
2. Choose standalone skill or plugin. For a plugin, split only workflows with independently meaningful activation and outputs; decide whether MCP is genuinely needed.
3. Before writing into an existing target or installing anything, check proposed skill and plugin names against that destination's discovery scope. Treat a collision as a decision to rename, revise the identified owned package, or obtain an explicit overwrite instruction; never overwrite an unrelated item.
4. Classify proposed files according to `portability-policy.md`. Keep client extensions isolated and documented.
5. Establish an observable acceptance contract, design the minimum files, and, for substantial projects, write an explicit spec and ordered plan. An example skill is not a mandatory scaffold.
6. Implement the portable package. For revisions, preserve unrelated files. Then complete these stages in order:
    - Review created/revised entries and references proportionately with [skill content review](skill-review.md), and assess a plugin with [plugin composition review](plugin-review.md). These checks inform authorized repairs without requiring a full audit of unrelated material.
    - After each skill's `SKILL.md` exists and its portable content is accepted, read [OpenAI presentation](openai-presentation.md) and generate context-specific `agents/openai.yaml` and `assets/icon.svg` for that skill. Review supplied brand/draft material before passing it as generator context.
    - Apply [validation policy](validation-policy.md): validate structure, run representative successful and failing workflows, inspect results, repair findings within scope, and revalidate.
7. Report output location, actual verification, runtime dependencies, portability limits and whether installation was separately performed.
