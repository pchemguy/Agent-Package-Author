## 📗 Problem Statement

> [!NOTE] Prompt
>  
>  I need to develop a compact description and a specific convenient model for a "Hello world!" skill-template for Codex/ChatGPT Work (and compatible with other systems) that must demo all key features: main file, progressive discovery (at least two different modules; more than one hierarchy level?), md resources/extras, python scripts (at least two), whatever else is important for a full complex skill. I need a good model task, for which the skill will be designed with natural decomposition (skill components outside main file) and meaningful readily testable outcomes of both md and py modules. I also need a proper vocabulary for articulating the problem/reqs.

You want something slightly more ambitious than a “Hello World” example: a **reference implementation / conformance fixture for the Agent Skills pattern**. It should remain small enough to inspect in minutes, while deliberately exercising discovery, progressive loading, references, executable helpers, assets, validation, and platform-specific metadata.

That matches the current OpenAI model well. Skills are directories centered on `SKILL.md`, with optional `scripts/`, `references/`, `assets/`, and OpenAI-specific `agents/openai.yaml`. Codex/ChatGPT initially see skill metadata, then load `SKILL.md`, and only subsequently read references or execute scripts when required. ([OpenAI Developers][1])

### 1. Vocabulary I would use

I would describe the design in terms of these concepts:

* **Skill bundle** — the complete portable directory.
* **Entry point / root instruction file** — `SKILL.md`.
* **Discovery metadata** — primarily `name` and `description`; this is what allows the runtime to decide whether the skill applies.
* **Activation / triggering** — automatic or explicit selection of the skill.
* **Orchestration layer** — the workflow in `SKILL.md`; it tells the agent what to inspect or execute rather than containing all domain knowledge itself.
* **Progressive disclosure** — loading deeper context only when needed.
* **Reference module** — Markdown containing declarative/domain knowledge that does not need to remain in the main skill context.
* **Reference hierarchy** — references that direct the agent to more specialized references.
* **Executable helper** — deterministic code in `scripts/`.
* **Asset** — an input/template intended to be copied, instantiated, or transformed rather than read primarily as instructions.
* **Fixture / example input** — stable sample data useful for demonstration and testing.
* **Artifact** — a file generated by running the skill.
* **Validation oracle** — something that can objectively say whether an artifact conforms.
* **Happy-path scenario** — canonical invocation that exercises the normal workflow.
* **Branch scenario** — invocation causing a different reference/module to be discovered.
* **Negative scenario** — deliberately invalid input/output demonstrating validation.
* **portable core** — files following the general Agent Skills conventions.
* **platform adapter** — optional OpenAI-, Claude-, etc.-specific metadata kept outside that portable core.
* **conformance surface** — the set of skill features the template intentionally demonstrates.
* **acceptance criteria** — observable conditions proving that each feature worked.

I'd call the whole thing a **minimal-complete reference skill**: minimal in domain complexity, complete in mechanism coverage.

### 2. The model task I think fits best

My preferred task would be a **Project Welcome Pack generator**.

The user supplies a tiny project description, for example:

> Create a welcome pack for `Acme Calculator`, a Python CLI that evaluates arithmetic expressions.  
> Audience: contributors.  
> Tone: friendly.  
> Variant: developer.

The skill produces something like:

```text
out/
├── WELCOME.md
└── welcome.json
```

`WELCOME.md` is the human artifact. `welcome.json` is a small machine-readable manifest describing what was generated and which rules/profile were used.

This is still recognizably “Hello World”: its essential job is to **welcome someone to a project**. But it is complex enough to justify a real skill architecture rather than contrived dummy modules.

More importantly, its parts naturally separate.

### 3. Natural decomposition

I would design the portable portion approximately like this:

```text
hello-world-skill/
├── SKILL.md
│
├── references/
│   ├── workflow.md
│   ├── output-contract.md
│   │
│   └── profiles/
│       ├── contributor.md
│       └── user.md
│
├── scripts/
│   ├── render.py
│   └── validate.py
│
├── assets/
│   └── welcome-template.md
│
├── examples/
│   ├── project.json
│   └── expected/
│       ├── WELCOME.md
│       └── welcome.json
│
└── agents/
    └── openai.yaml
```

The first three directories line up with the documented skill structure; `examples/` is our own convention rather than something the portable specification needs to understand. OpenAI currently documents `agents/openai.yaml` separately as optional appearance/dependency metadata, which is a good reason to treat `agents/` as a **platform adapter** rather than part of the portable behavioral core. ([OpenAI Developers][1])

#### Why the hierarchy is meaningful

The progressive path might be:

```text
discovery metadata
    ↓
SKILL.md
    ↓
references/workflow.md
    ↓
references/profiles/contributor.md
```

That is much better than putting three arbitrary Markdown files next to one another just to prove that they exist.

The agent reads:

1. `SKILL.md` because the skill activates.
2. `workflow.md` because this particular operation requires generation.
3. `profiles/contributor.md` because the user requested a contributor welcome pack.
4. It does **not** need `profiles/user.md`.

That demonstrates actual selective context acquisition.

I would absolutely include the second reference hierarchy level. Otherwise you demonstrate “external references,” but not convincingly **progressive** discovery.

### 4. Each component should have a distinct responsibility

`SKILL.md` should stay compact. It should define applicability, required input, the top-level workflow, decision points, which references to consult, which scripts to run, and completion criteria. OpenAI explicitly recommends skills as reusable workflows and describes `SKILL.md` as the playbook containing inputs, workflow, output expectations, and final checks. ([OpenAI][2])

`references/workflow.md` should explain the transformation rules in enough detail that there is a real reason not to duplicate them in `SKILL.md`.

`references/output-contract.md` should define things such as mandatory Markdown sections, JSON fields, allowed values, normalization rules, and invariants.

`references/profiles/contributor.md` might require sections such as:

```text
Hello, <project>!
What it does
First contribution
Where to start
```

while `references/profiles/user.md` might instead require:

```text
Hello, <project>!
What it does
Quick start
Where to get help
```

This is actual domain knowledge whose effect can be observed in the resulting artifact.

### 5. The two Python scripts should not be redundant

This is important. Don't make `foo.py` and `bar.py` just to meet a checklist.

#### `render.py`

A deterministic transformation:

```text
project facts
+ selected profile
+ template
→ WELCOME.md
+ welcome.json
```

It demonstrates the skill invoking code when deterministic transformation is preferable to asking the model to manually reproduce formatting.

For example:

```console
python scripts/render.py \
    --input examples/project.json \
    --profile contributor \
    --output out
```

The script should have simple, dependency-free behavior where practical.

#### `validate.py`

An independent checker:

```text
generated artifact
+ output contract
→ pass/fail diagnostics
```

For example:

```console
python scripts/validate.py out
```

with:

```text
OK: WELCOME.md
OK: welcome.json
OK: profile=contributor
OK: 4 required sections present
```

and a nonzero exit status on failure.

This gives you a valuable pattern:

> **generator + independent validator**

rather than two arbitrary utilities.

It makes the skill self-checking and gives Codex/Work a meaningful reason to execute both programs.

### 6. Markdown references must also have observable effects

A common weakness in demo skills is that the documentation exists, but there is no way to know whether the model actually used it.

Your template should deliberately prevent that.

For example `profiles/contributor.md` can contain a unique but sensible requirement:

```markdown
For the contributor profile, the final section MUST be
`First tiny change` and must contain exactly one concrete
repository-local starter task.
```

The expected artifact then proves that this reference influenced behavior.

Likewise `output-contract.md` might say:

```markdown
`welcome.json` must contain:

- `schema_version`
- `project`
- `profile`
- `sections`
- `generated_by`

`schema_version` must equal `1`.
```

`validate.py` can test those rules.

Now both the `.md` and `.py` components produce **externally observable consequences**.

### 7. An even stronger progressive-discovery branch

If you want to demonstrate deeper routing, I would add one more dimension:

```text
references/
└── profiles/
    ├── contributor.md
    └── user.md
        └── ...
```

But don't create directories merely for depth.

A more legitimate hierarchy would be:

```text
references/
├── workflow.md
├── output-contract.md
└── profiles/
    ├── contributor.md
    └── audiences/
        ├── technical.md
        └── nontechnical.md
```

Then `contributor.md` could say:

> Determine whether the requested audience is technical or nontechnical and read the appropriate file under `profiles/audiences/`.

This exercises:

```text
SKILL
→ profile
→ sub-profile
```

Yet I would keep that as the **extended demonstration**, not necessarily the baseline. One genuine nested selection is enough to prove recursive progressive disclosure.

### 8. What `SKILL.md` itself should demonstrate

The main file should exercise six things explicitly:

```text
1. Discovery
   Clear name + description.

2. Applicability
   When to use / when not to use the skill.

3. Input normalization
   Required vs optional input and defaults.

4. Conditional discovery
   Which reference to read under which condition.

5. Execution
   When to invoke render.py and validate.py.

6. Completion
   What constitutes a successful result.
```

The main file should **not** repeat all profile rules and output schema details. Otherwise the references cease to demonstrate progressive disclosure.

The documented runtime behavior supports precisely this model: metadata is seen first; full `SKILL.md` is loaded when the skill is selected; references and scripts are then used only as needed. ([OpenAI Developers][3])

### 9. I would include assets, examples, and tests—but distinguish them

A particularly useful distinction is:

```text
references/     agent-readable knowledge
scripts/        agent-executable behavior
assets/         material consumed/copied by the workflow
examples/       demonstration and test fixtures
tests/          repository-level verification of the skill package
```

If this is supposed to be a development template rather than merely an installable skill, I'd actually add:

```text
tests/
├── test_render.py
└── test_validate.py
```

Then you have **two validation layers**:

* `scripts/validate.py` is part of the *runtime workflow* and validates generated output.
* `tests/` validates the *implementation of the skill itself*.

That distinction is useful enough that I would deliberately teach it in the template.

### 10. The resulting full reference layout

So my preferred complete example becomes:

│
├── references/
│   ├── workflow.md
│   ├── output-contract.md
│   └── profiles/

│       └── user.md
│
├── scripts/
│   ├── render.py
│   └── validate.py
│
├── assets/
│   └── welcome-template.md
│
├── examples/
│   ├── contributor.json
│   ├── user.json
│   └── expected/
│       ├── contributor/
│       │   ├── WELCOME.md
│       │   └── welcome.json
│       └── user/
│           ├── WELCOME.md
│           └── welcome.json

There is almost nothing decorative here. Every major path demonstrates a distinct mechanism.

### 11. Concrete acceptance scenarios

The canonical scenario should be something like:

> **Create a contributor welcome pack for Example Calculator from `examples/contributor.json`.**

Expected behavior:

```text
SKILL.md selected
    ↓
workflow.md read
    ↓
output-contract.md read
    ↓
profiles/contributor.md read
    ↓
assets/welcome-template.md consumed
    ↓
render.py executed
    ↓
WELCOME.md + welcome.json created
    ↓
validate.py executed
    ↓
validation succeeds
```

Then have a second scenario:

> **Create a user welcome pack for the same project.**

This should select `profiles/user.md` instead and produce observably different content.

Finally, a negative scenario can corrupt `welcome.json` or delete a required heading and demonstrate:

```console
$ python scripts/validate.py out
ERROR: WELCOME.md: missing required section 'First tiny change'
```

That is a genuinely useful demonstration.

### 12. What the template is actually demonstrating

I would state the purpose of the repository approximately this way:

> **Hello World Skill is a minimal-complete reference implementation of an Agent Skill. It demonstrates skill discovery, activation, orchestration through `SKILL.md`, hierarchical progressive disclosure of Markdown references, deterministic script execution, reusable assets, conditional workflow branches, artifact generation, and independent validation while keeping the underlying task intentionally small.**

That is the **compact description** I think you are looking for.

And the design principle underneath it is:

> **Every component included in the template must either affect an observable result or verify one.**

That rule prevents the example from degenerating into a kitchen-sink directory tree.

I think the **Project Welcome Pack** is substantially better than literal greeting generation because it preserves the conceptual “Hello World” identity while providing natural branching, references, assets, scripts, generated artifacts, and validation without inventing artificial complexity. It also remains platform-neutral: the portable core follows the Agent Skills organization, while things such as `agents/openai.yaml` can remain cleanly isolated as adapter metadata. OpenAI explicitly describes the format as portable and usable across tools supporting Agent Skills, including Codex. ([OpenAI Academy][4])

If you pursue this model, the next useful step is to formalize it as a **one-page template specification** defining the conformance surface, exact tree, required demonstration scenarios, and acceptance criteria before writing the actual files.

## 📗 Compatibility Assessment

> [!NOTE] Prompt
>  
>  Assess first how this structure aligns with de-factor standard (say, I want to be able to use it with Gemini and a local Agent).

Yes. The structure is already close to the current **Agent Skills de-facto/open standard**, but I would change a few things if the objective is specifically:

> **one skill bundle that works essentially unchanged in Codex/ChatGPT, Gemini, and a generic/local Agent Skills-compatible harness.**

The important development since the earlier answer is that this is no longer merely an OpenAI convention. There is an explicit Agent Skills specification, and both OpenAI and Google now document `SKILL.md`-based skills. OpenAI explicitly states compatibility with the open Agent Skills standard, while Google's current Gemini tooling also supports `.agents/skills/<skill>/SKILL.md`. ([GitHub][1])

### The actual portable core

The strongest common denominator is:

```text
hello-world/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

That is almost exactly the canonical Agent Skills structure:

```text
skill-name/
├── SKILL.md          # required
├── scripts/          # optional executable code
├── references/       # optional documentation
├── assets/           # optional templates/resources
└── ...               # other files/directories allowed
```

The standard requires YAML frontmatter in `SKILL.md`, with at least `name` and `description`; scripts, references, and assets are conventional optional components. ([GitHub][1])

So **that should be the normative template**, rather than an OpenAI-specific layout.

#### One correction: nested references are not a good conformance demonstration

My earlier proposal had:

```text
references/
└── profiles/
    ├── contributor.md
    └── user.md
```

and even contemplated:

```text
references/
└── profiles/
    └── audiences/
        └── technical.md
```

I would now **not** use that in the canonical Hello World skill.

It is technically legal—the standard permits arbitrary additional files and directories—but the Agent Skills specification explicitly recommends:

> keep file references one level deep from `SKILL.md` and avoid deeply nested reference chains. ([GitHub][1])

This distinction is important:

**progressive disclosure is a context hierarchy, not a filesystem-depth exercise.**

The canonical three stages are:

```text
Level 1   discovery metadata
          name + description

Level 2   activated instructions
          SKILL.md

Level 3   on-demand resources
          references/*, scripts/*, assets/*
```

That is the hierarchy worth demonstrating. ([GitHub][1])

You do **not** gain anything standards-wise from:

```text
SKILL.md
→ references/foo.md
→ references/foo/bar.md
→ references/foo/bar/baz.md
```

In fact, it demonstrates a pattern the reference specification discourages.

#### Better layout

I'd flatten the resource namespace:

```text
hello-world/
├── SKILL.md
│
├── references/
│   ├── workflow.md
│   ├── output-contract.md
│   ├── profile-contributor.md
│   └── profile-user.md
│
├── scripts/
│   ├── render.py
│   └── validate.py
│
└── assets/
    └── welcome-template.md
```

You still demonstrate selective progressive disclosure:

```text
metadata
   ↓
SKILL.md
   ├── workflow operation ─────→ references/workflow.md
   ├── output requirements ────→ references/output-contract.md
   └── profile=contributor ────→ references/profile-contributor.md
```

`profile-user.md` remains unloaded.

That is actually a **better test of progressive disclosure** than nested directories.

#### Codex / ChatGPT alignment

This structure is essentially native.

OpenAI currently documents precisely:

```text
my-skill/
├── SKILL.md
├── scripts/
├── references/
├── assets/
└── agents/
    └── openai.yaml
```

and Codex performs progressive loading from `name`/`description` → `SKILL.md` → supporting resources. ([OpenAI Developers][2])

Repository-level Codex discovery uses `.agents/skills` while traversing from the working directory toward the repository root. ([OpenAI Developers][3])

So an installation can simply be:

```text
repo/
└── .agents/
    └── skills/
        └── hello-world/
            ├── SKILL.md
            ├── references/
            ├── scripts/
            └── assets/
```

No translation required.

#### Gemini alignment is now unusually good

Google's current managed-agent documentation gives almost the same arrangement:

```text
my-agent/
├── AGENTS.md
├── skills/
│   └── slide-maker/
│       └── SKILL.md
└── workspace/
```

and specifically documents automatic discovery from:

```text
.agents/
└── skills/
    └── slide-maker/
        └── SKILL.md
```

([Google AI for Developers][4])

Google also has a current Gemini CLI codelab teaching Agent Skills directly and placing them at:

```text
.agents/skills/my-favorite-things/SKILL.md
```

([Google Codelabs][5])

This gives us an especially useful common installation convention:

```text
.agents/skills/<skill-name>/
```

works naturally for both current Codex and current Gemini tooling.

That is stronger interoperability than I would have assumed historically.

### What is *not* portable core

This is where I would alter the previous model.

##### `agents/openai.yaml`

This is **OpenAI-specific**.

OpenAI documents it as optional metadata for appearance/dependencies. ([OpenAI Developers][2])

Therefore:

```text
agents/
└── openai.yaml
```

should not be portrayed as a normal component of an Agent Skill.

It is better characterized as:

> **implementation-specific extension metadata**

It can exist in the reference repository, but the skill must behave correctly without it.

For a portability demonstration, I'd potentially include it deliberately but label it clearly:

```text
agents/
└── openai.yaml       # optional OpenAI adapter; not portable core
```

This actually gives the template pedagogical value: it teaches the distinction between **standard skill content** and **host-specific extensions**.

### `examples/` is fine, but isn't standard semantics

The Agent Skills specification explicitly permits arbitrary additional files/directories. ([GitHub][1])

Thus:

```text
examples/
```

is entirely acceptable.

But a generic Agent Skills implementation has no obligation to give `examples/` any special behavior.

So I would call it:

> **repository support material**, not a skill primitive.

The same applies to:

```text
tests/
```

They are useful for developing the skill but have no special runtime semantics.

That suggests an important architectural distinction.

```text
hello-world/
│
├── SKILL.md                 # Agent Skills standard
├── references/              # Agent Skills convention
├── scripts/                 # Agent Skills convention
├── assets/                  # Agent Skills convention
│
├── examples/                # project convention
├── tests/                   # project convention
│
└── agents/
    └── openai.yaml          # host-specific extension
```

That's a very good teaching structure.

### What about `evals/`?

There is growing usage of an `evals/` directory in Agent Skills repositories, and some reference-skill projects recommend it, often containing machine-readable prompt/assertion cases. But it is **not part of the small normative core** in the same way as `SKILL.md`, `scripts/`, `references/`, and `assets/`. ([GitHub][6])

For our Hello World template I think it is worth including, but explicitly as:

> **portable evaluation convention**, rather than required runtime structure.

For example:

```text
evals/
└── evals.json
```

could contain:

```json
[
  {
    "id": "contributor-pack",
    "prompt": "Create a contributor welcome pack for Example Calculator.",
    "assertions": [
      "Uses the contributor profile",
      "Creates WELCOME.md",
      "Creates welcome.json",
      "Runs output validation"
    ]
  }
]
```

That gives local-agent implementors something extremely useful, even if their harness doesn't understand `evals/` automatically.

### Local agents are the interesting case

There are really two levels of compatibility.

##### Agent Skills-aware local agent

If your local harness implements the Agent Skills specification, then we should expect roughly:

1. scan configured skill directories;
2. parse `SKILL.md` frontmatter;
3. initially expose only `name` and `description`;
4. select/activate a skill;
5. load the `SKILL.md` body;
6. provide filesystem access so the model can read resources and execute scripts.

That is enough to consume this template essentially unchanged.

The open specification explicitly defines the progressive-disclosure model as metadata → instructions → resources. ([GitHub][1])

This is therefore a very reasonable target for your own local agent.

##### Generic local agent with no Agent Skills support

No directory structure can magically make that interoperable.

You need a tiny **skill loader/adapter** that translates the standard into whatever the harness understands.

But that adapter can be extremely thin because the skill itself remains portable.

Conceptually:

```text
              portable skill
                   │
             hello-world/
                   │
     ┌─────────────┼─────────────┐
     ↓             ↓             ↓
   Codex        Gemini       local loader
     │             │             │
 native          native        adapter
```

That is the architecture I'd target.

### Frontmatter matters more than vendor metadata

For maximum portability, the canonical `SKILL.md` should use only standard frontmatter unless we have a particular reason otherwise.

Something like:

```yaml
---
name: hello-world
description: >
  Generate and validate a small project welcome pack.
  Use this skill when demonstrating, testing, or learning
  Agent Skills workflows and progressive disclosure.
---
```

The standard defines `name` and `description` as required. It also defines optional fields including `license`, `compatibility`, `metadata`, and the experimental `allowed-tools`, whose support may vary. ([GitHub][1])

For **Hello World**, I would avoid `allowed-tools`.

It's specifically documented as experimental and implementation-dependent, making it a poor feature for the core interoperability example.

`compatibility`, however, may eventually be useful if we say something concrete such as:

```yaml
compatibility: Requires Python 3.10 or later.
```

But even that should probably come after we establish the minimal baseline.

### Python is a very good choice for scripts

For a cross-harness template, Python is arguably the best executable demonstration.

The Agent Skills spec intentionally does not prescribe an executable language; it notes Python, Bash, and JavaScript as common choices and says runtime support depends on the agent implementation. ([GitHub][1])

For our purposes:

```text
scripts/render.py
scripts/validate.py
```

are preferable to shell scripts because they are much more portable across:

* Windows,
* Linux,
* macOS,
* Codex environments,
* Gemini environments,
* local harnesses.

I would make them:

* standard-library only;
* deterministic;
* invocable using `python scripts/...`;
* independent of cwd where practical;
* returning conventional exit codes;
* producing concise stdout/stderr diagnostics.

That gives us a meaningful **execution portability test** in addition to a skill-format portability test.

#### One other architectural choice: don't put `AGENTS.md` or `GEMINI.md` inside the skill

I would keep **agent-wide/repository-wide instructions separate from skill instructions**.

For example an installed repository might be:

```text
project/
├── AGENTS.md
├── GEMINI.md             # only if the particular Gemini setup needs it
│
└── .agents/
    └── skills/
        └── hello-world/
            ├── SKILL.md
            ├── references/
            ├── scripts/
            └── assets/
```

The skill itself shouldn't depend on repository-level control files.

That keeps the package transferable:

### Integrated design principles

I would make the template satisfy these requirements simultaneously:

1. **Portable skill core only.** No `agents/openai.yaml`, Gemini-only metadata, Claude-only metadata, host-specific tool declarations, or experimental frontmatter fields.
2. **Demonstrate every important portable mechanism.** Discovery metadata, compact orchestration in `SKILL.md`, conditional progressive disclosure, Markdown references, executable scripts, static assets, artifact production, deterministic validation, and realistic branch behavior.
3. **Every component has an observable purpose.** No files added merely to make the directory tree look complex.
4. **Progressive disclosure must be testable.** Different invocations should require different references; an irrelevant reference should not need to be loaded.
5. **Keep resource topology shallow.** All resources should be directly reachable from `SKILL.md`; avoid `SKILL.md → A.md → B.md` chains. This follows the current specification's recommendation and makes weaker/local harnesses less likely to fail. ([GitHub][1])
6. **Scripts must be maximally portable.** Python, standard library only, deterministic, no network, explicit CLI, conventional exit codes.
7. **Runtime skill vs development material must be clearly separated conceptually**, even if both live in the repository.

### `SKILL.md` should be an orchestrator, not a manual

The main file should contain only:

* discovery metadata;
* applicability;
* input requirements/defaults;
* high-level workflow;
* conditional routing;
* exact resource/script paths;
* validation/completion conditions;
* concise failure handling.

For example, conceptually:

```text

3. Read references/output-contract.md.
4. If audience=contributor, read references/contributor-profile.md.
   If audience=user, read references/user-profile.md.
5. Use assets/welcome-template.md.
6. Run scripts/render.py.
7. Run scripts/validate.py.
8. Do not report success unless validation passes.
```

```text
discovery
name + description
      ↓
activation
SKILL.md
      ↓
task-dependent resources
workflow.md
output-contract.md
contributor-profile.md OR user-profile.md
template
scripts
```

The Agent Skills spec explicitly describes this three-stage loading model. ([GitHub][1])

### Why four reference files are justified

Each should test a different kind of declarative resource.

`workflow.md` demonstrates **procedural reference material**. It contains transformation rules too detailed for the main orchestration file.

`output-contract.md` demonstrates **normative contract material**. It defines required files, sections, JSON fields, field types, invariants, naming rules, etc.

`contributor-profile.md` and `user-profile.md` demonstrate **conditional domain/reference loading**.

This gives us two distinct progressive-disclosure dimensions:

```text
always needed:
    workflow.md
    output-contract.md

conditionally needed:
    contributor-profile.md
        OR
    user-profile.md
```

That is better than introducing deeper filesystem nesting just to show “multiple levels.”

### The Markdown modules need observable consequences

For example, `contributor-profile.md` could require:

```text
The final Markdown section must be "First tiny change".

That section must contain exactly one concrete starter task.
```

`user-profile.md` might instead require:

```text
The final Markdown section must be "Where to get help".

Do not include repository-contribution instructions.
```

Then the generated output proves which reference was used.

Likewise, `output-contract.md` might define:

```text
welcome.json must contain:
- schema_version
- project
- audience
- sections
- generated_by

schema_version must equal 1.
```

These rules can then be verified mechanically.

That is important: **a reference file should not merely be readable; it should affect a testable outcome.**

### The two scripts have distinct roles

#### `render.py`

This is the deterministic producer:

```text
normalized input
+ selected profile
+ template
→ WELCOME.md
+ welcome.json
```

Example invocation:

```console
python scripts/render.py \
    --input examples/contributor.json \
    --output out
```

It should:

* use only the standard library;
* use stable ordering;
* avoid timestamps unless explicitly controlled;
* produce deterministic bytes for identical input;
* fail cleanly on malformed input;
* return nonzero on error.

#### `validate.py`

This is an independent validation oracle:

```text
output directory
→ success or actionable errors
```

Example:

```console
python scripts/validate.py out
```

Success:

```text
OK: WELCOME.md
OK: welcome.json
OK: audience=contributor
OK: required sections present
```

Failure:

```text
ERROR: WELCOME.md: missing required section "First tiny change"
```

This producer/validator separation is one of the strongest features of the model because it demonstrates a general best practice for reliable agent workflows:

```text
generate → validate → repair if needed → validate again
```
