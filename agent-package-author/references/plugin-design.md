# Plugin design

Choose a plugin when packaging multiple independently useful skills or a skill with optional MCP configuration. Split skills where activation, workflow, resources, outputs or lifecycle are independently meaningful; keep branches of one capability in a single skill. Distinguish plugin identity from each skill name and avoid overlapping trigger descriptions.

Keep shared material under explicit ownership. When skills are distributed together, use ordinary relative Markdown links for intentional sibling references. Link to `../other-skill/SKILL.md` and name **other-skill** in prose when requesting a workflow handoff. Link directly to `../other-skill/references/topic.md` when loading shared guidance without selecting the sibling workflow. Check that each resolved file stays within the plugin root. A skill intended to work in isolation needs its own copy of required guidance; a sibling link makes it dependent on the bundle.

## Shared plugin entries and coordination

`PLUGIN.md` at the plugin root is an optional **shared orientation document**, not a portable Agent Plugins 1.0.0 component or automatically discovered entry. Use it only when the target environment has an explicit loading path and cross-skill navigation has value. Name that loading path in the package's use instructions. It may summarize capabilities, composite triggers, common prerequisites, principal owners, outputs, handoffs and stops. Keep substantial operational rules in supported skill entries or their owned references, so direct entry and follow-up work still function when `PLUGIN.md` is unavailable.

A **coordinator** is an ordinary bundled skill under `skills/<name>/SKILL.md` whose capability is cross-skill selection and orchestration. It has no standardized role field or automatic invocation. Add one only when recurring selection, shared readiness, continuity, handoff or return needs a canonical owner. Its entry identifies the available paths and consequential gates before dependent work; its references can hold cohesive orchestration detail. Focused skills retain their procedures and direct entry for focused requests. A coordinator neither requires `PLUGIN.md` nor follows merely from plugin size or a single composite path; an optional `PLUGIN.md` can summarize its routes but cannot be its only instruction source.

Define a **composite workflow** when one request meaningfully joins independently useful skills or components. State its trigger, common prerequisites, principal owners, consequential order and handoff inputs/results, output and stop in a discoverable skill entry, using a coordinator when the ownership test above warrants one. Link to each focused owner's instructions rather than duplicating their procedures. A shared `PLUGIN.md` may project a concise summary when its loading path exists. A named cross-skill handoff documents routing; the target client controls activation.

Only `skills/*/SKILL.md` immediate children are portable skills. A named handoff and link identify another capability; they do not guarantee that a client activates it. Do not imply that arbitrary `commands/`, hooks, custom agents, or rules are portable v1 components. Explicit client-specific behavior belongs under the client's verified reverse-domain `extensions` namespace and/or matching root directory; this is not portable core. Installation and presentation remain client concerns.

Read `openai-presentation.md` to generate distinct OpenAI presentation in each immediate-child skill after the portable plugin is designed. Do not put a skill's OpenAI metadata at plugin root or in `plugin.json`.
