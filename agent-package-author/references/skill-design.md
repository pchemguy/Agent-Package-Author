# Skill design

Define one coherent capability and its activation phrases. Put orchestration, conditions, and completion gates in a compact `SKILL.md`; move focused guidance for identifiable workflow components to references, repeated deterministic operations to scripts, and reusable input material to assets. A simple skill can consist of `SKILL.md` alone.

Load only task-relevant references; when two branches require different knowledge, make the branch observable in an output or decision. For a skill with `references/*.md`, put a concise, identified routing section in `SKILL.md` that names and directly links each reference with its purpose, boundary and loading condition. This is APA authoring policy, not an Agent Skills format requirement. A skill with no references needs no routing section. Use [skill review](skill-review.md) to assess entry-only selection and the actual reference content. Avoid redundant prose and deep reference chains. Scripts declare runtime dependencies and errors. If a script generates artifacts that can be checked independently, define an independent validator rather than trusting the producer.

When one skill has a meaningful composite path through multiple references, `SKILL.md` may add a short **Composite workflows** section if the reference routing alone does not explain that path. For each such path, name its trigger, linked reference owners and their roles, consequential order or handoffs, output and stop. Keep detailed procedures in their owning references; the entry summarizes selection and coordination. Several independent reference choices, or a composite already clear from the entry, need no extra section. This is optional APA design guidance, not a portable format field or a second skill entry.

Choose reference boundaries by coherent responsibility and use, not file length. Each reference should define a particular component of the skill's workflow: a selected procedure, decision rule, shared operational constraint, check or handoff whose use changes what the agent does. Supporting explanation belongs with the component it serves. Put standalone examples and background in the source repository's root `README.md` or root `examples/` as appropriate. Include an `examples/` directory inside the skill package only when an actual runtime step needs those files, the entry exposes their loading path, and their inclusion has a strong, specific justification; that directory is not a discovered workflow entry. A broad guide may be shallow; a narrower procedure may need more detail. Each reference should contain enough substance for its own role and have a clear loading condition, including genuinely shared use. Keep a thin fragment with its caller or neighboring owner when it has no independent use. Split a broad reference only when it contains a distinct, substantial subworkflow with a caller-visible trigger. Preserve shared prerequisites, the route from `SKILL.md`, and the return or handoff after a split. Do not divide one cohesive procedure merely to reach a size target.

Design representative success, branch, and negative acceptance cases based on actual behavior. Use the smallest structure that explains and validates the requested workflow. Describe execution requirements separately from structural format conformance.
